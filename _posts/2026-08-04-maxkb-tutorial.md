> MaxKB 是 1Panel-dev 开源的企业级智能体平台，核心能力包括知识库问答、RAG Pipeline、工作流编排、MCP 工具调用、多模型接入和第三方系统集成。本文写一份面向个人开发者和中小团队的实操教程：先跑起来，再接模型、建知识库、做智能体，最后补上生产环境要注意的安全、备份和评估问题。

## 一、MaxKB 适合解决什么问题

MaxKB 的定位不是“又一个聊天界面”，而是一个面向企业知识和业务流程的智能体平台。它把几个常见能力放在同一个产品里：模型管理、知识库、文档切分、向量化、检索问答、工作流、工具调用、智能体发布和嵌入。

更具体地说，它适合这些场景。

| 场景 | 典型问题 | MaxKB 的价值 |
| --- | --- | --- |
| 企业内部知识库 | 制度、手册、FAQ、产品文档分散，员工很难检索 | 上传文档后做 RAG 问答，并能看到引用来源 |
| 客服问答助手 | 大量重复咨询，人工客服成本高 | 用知识库兜底常见问题，复杂问题再转人工 |
| 售前/交付助手 | 方案、报价、部署手册需要反复查资料 | 按业务资料生成结构化回答，提高响应速度 |
| 运维知识助手 | 故障处理 SOP 和日志分析经验分散 | 把操作手册、故障库、脚本工具接入智能体 |
| 教育与培训 | 课程资料、论文、教材需要交互式问答 | 以知识库为中心做学习助手 |

如果你的需求只是本地和模型随便聊聊，Ollama + Open WebUI 可能更轻；如果你要的是“文档知识库 + 可发布智能体 + 业务系统嵌入”，MaxKB 的抽象更直接。

## 二、整体架构：先理解几个核心模块

MaxKB 的主界面通常围绕五类资源展开。

| 模块 | 作用 | 使用时的关键点 |
| --- | --- | --- |
| 首页 | 查看资源概览、运营监控和使用情况 | 生产环境要关注使用量、失败率和热点资源 |
| 模型 | 对接大语言模型、向量模型、语音、视觉等模型 | 至少需要一个 LLM；做 RAG 时还需要向量模型 |
| 知识库 | 管理文档、网页、分段、向量化和命中测试 | 文档质量和切分策略决定问答质量上限 |
| 工具 | 管理函数、MCP 工具、外部 API 调用 | 用于让智能体从“回答问题”变成“执行任务” |
| 智能体 | 创建简易智能体或高级智能体工作流 | 负责把模型、知识库、工具和提示词组合成应用 |

一个典型请求链路是：

1. 用户在问答页或第三方系统里提问。
2. 智能体接收问题，按配置决定是否改写问题、检索知识库、调用工具。
3. 知识库根据向量检索、全文检索或混合检索返回相关分段。
4. 智能体把问题、提示词、历史记录、检索结果和工具结果组装给模型。
5. 模型生成答案，MaxKB 返回结果并记录日志。

这套链路的好处是工程边界清楚：文档归知识库，模型归模型管理，流程归智能体，外部动作归工具。后续调优时不会全部混在一个提示词里。

## 三、部署 MaxKB

MaxKB 官方提供多种部署方式。个人开发、测试环境可以直接 Docker 跑；生产环境官方更推荐使用离线安装包。本文先给最短路径，再给生产建议。

### 1. 测试环境：Docker 快速启动

准备一台已经安装 Docker 的机器，然后执行：

```bash
docker run -d \
  --name=maxkb \
  --restart=always \
  -p 8080:8080 \
  -v ~/.maxkb:/opt/maxkb \
  1panel/maxkb
```

启动后访问：

```text
http://服务器IP:8080
```

默认管理员账号：

```text
用户名：admin
默认密码：MaxKB@123..
```

首次登录后建议立刻修改默认密码。这个步骤不要拖，因为默认账号密码一旦暴露在公网环境里风险很高。

### 2. 生产环境：优先考虑离线安装

生产环境建议按官方 V2 文档使用离线安装包。原因很直接：

| 维度 | Docker 单容器快速启动 | 离线安装包 |
| --- | --- | --- |
| 适用场景 | 本地测试、个人试用、功能验证 | 生产部署、内网部署、稳定运行 |
| 依赖管理 | 依赖宿主机 Docker 环境 | 安装包内带推荐 Docker / Compose 版本 |
| 升级迁移 | 需要自己确认数据目录和版本兼容 | 官方文档覆盖迁移、备份、还原、命令行工具 |
| 运维控制 | 简单但可控项少 | 更适合标准化运维 |

官方 FAQ 提到，Docker 版本过老可能导致安装失败；安装包内使用的 Docker 版本为 27.2.0、Compose 版本为 v2.29.2。实际部署时应把 Docker、Compose、MaxKB 版本一起纳入变更记录。

### 3. 基础检查命令

部署完成后先做这几个检查。

```bash
docker ps
docker logs --tail=100 maxkb
curl -I http://127.0.0.1:8080
```

如果页面无法访问，按顺序检查：

| 问题 | 排查点 |
| --- | --- |
| 容器没起来 | `docker ps -a` 看状态，`docker logs maxkb` 看报错 |
| 端口不通 | 确认 `-p 8080:8080`，检查安全组、防火墙、反向代理 |
| 数据目录异常 | 确认挂载目录存在且权限正确 |
| 升级后模块缺失 | 查看 Python 依赖目录和官方升级 FAQ |

## 四、接入模型：LLM 和向量模型都要考虑

MaxKB 支持对接本地模型和主流云模型。官方文档列出的模型供应商包括 OpenAI、Anthropic、Azure OpenAI、Gemini、DeepSeek、Kimi、智谱、阿里云百炼、火山引擎、腾讯混元、百度千帆、Ollama、vLLM 等。

在使用上建议分两步：

1. 先接一个稳定的聊天模型，验证普通问答。
2. 再接向量模型，验证知识库导入和命中。

### 1. 云模型接入思路

以 OpenAI 兼容服务、DeepSeek、阿里云百炼或其他供应商为例，通常需要这些参数：

| 参数 | 含义 |
| --- | --- |
| 模型名称 | 在 MaxKB 里显示的名字，例如 `deepseek-chat`、`qwen-plus` |
| 模型类型 | 大语言模型、向量模型、语音识别、图像理解等 |
| 基础模型 | 供应商实际模型 ID |
| API Key | 供应商控制台生成的密钥 |
| Base URL | OpenAI 兼容服务或私有网关地址，部分供应商需要 |

接入后先用最简单的问题测试，例如：

```text
请用三句话解释什么是 RAG。
```

不要一开始就测试复杂业务问题。先验证模型连通性，再验证知识库检索，否则问题来源很难判断。

### 2. 本地模型接入思路

如果你已经部署了 Ollama 或 vLLM，可以把 MaxKB 作为应用层，把本地模型作为推理层。

常见组合如下。

| 推理后端 | 适合场景 | 注意点 |
| --- | --- | --- |
| Ollama | 单机、本地测试、小团队私有化 | 模型管理简单，但高并发能力有限 |
| vLLM | GPU 服务器、高吞吐 OpenAI 兼容 API | 需要关注显存、并发、KV Cache 和模型参数 |
| 云厂商 API | 快速上线、免维护 | 成本、数据合规和网络稳定性要评估 |

个人环境可以先用云模型降低变量；企业内网环境则可以用 vLLM 或 Ollama 接 Qwen、DeepSeek、Llama 等模型。

## 五、创建知识库：RAG 效果的核心在这里

MaxKB 支持上传 Markdown、TXT、PDF、DOCX、HTML、XLS、XLSX、CSV、ZIP 等文件，也支持网站知识库等形式。知识库不是“把文件扔进去就完事”，它至少涉及四个关键步骤。

![MaxKB tutorial workflow](/assets/images/maxkb-tutorial/workflow.svg)

### 1. 准备文档

建议优先整理出结构清晰的 Markdown、HTML 或 DOCX。PDF 虽然方便上传，但复杂排版、页眉页脚、扫描件、双栏论文都可能影响解析效果。

文档准备原则：

| 原则 | 说明 |
| --- | --- |
| 一个文件聚焦一个主题 | 避免一个文档同时混入制度、FAQ、变更记录和接口说明 |
| 标题层级清楚 | Markdown 的 `#`、`##`、`###` 会帮助切分 |
| 段落语义完整 | 每个分段最好能独立回答一个小问题 |
| 去掉噪声内容 | 页脚、版权声明、目录重复、无意义表格会污染检索 |
| 保留关键术语 | 不要把产品名、接口名、参数名改成口语化表达 |

### 2. 选择分段策略

MaxKB 支持智能分段和高级分段。

| 分段方式 | 适合文档 | 使用建议 |
| --- | --- | --- |
| 智能分段 | Markdown、标题层级明确的手册 | 优先选择，维护成本低 |
| 高级分段 | FAQ、日志、合同、表格化知识 | 用分隔符、长度、正则做精细控制 |

一个经验值：不要让分段过短，也不要让分段过长。过短会丢上下文，过长会引入噪声。对产品文档、FAQ、制度文档来说，单段 300 到 1000 中文字通常更容易调试；最终仍要通过命中测试验证。

### 3. 做命中测试

知识库导入完成后，不要直接发布智能体。先准备 20 到 50 个真实问题做命中测试。

测试样例可以覆盖：

| 类型 | 示例 |
| --- | --- |
| 精确事实 | “试用账号默认有效期是多少天？” |
| 流程操作 | “如何申请合同审批？” |
| 异常处理 | “登录失败提示账号不存在怎么办？” |
| 术语解释 | “什么是项目交付验收单？” |
| 边界问题 | “海外员工是否适用这条报销规则？” |

观察重点不是模型回答是否流畅，而是检索结果是否命中正确分段。如果检索结果错了，后面的模型生成越流畅越危险。

## 六、创建智能体：从简易智能体开始

MaxKB 支持简易智能体和高级智能体。第一次使用建议从简易智能体开始。

### 1. 简易智能体配置

进入智能体页面，创建一个智能体，完成这些配置：

| 配置项 | 建议 |
| --- | --- |
| 名称 | 使用业务可识别名称，例如“运维手册助手” |
| 描述 | 写清楚回答范围，避免用户误用 |
| AI 模型 | 选择已验证可用的大语言模型 |
| 系统提示词 | 定义角色、边界、回答格式和拒答规则 |
| 历史聊天记录 | 内部知识问答通常不宜过长，避免旧上下文干扰 |
| 关联知识库 | 绑定刚才创建并测试过的知识库 |
| 检索模式 | 优先尝试混合检索；数据量小可先用向量检索 |
| 相似度阈值 | 从中等阈值开始，结合命中测试调参 |
| 引用分段数 TopK | 常见范围 3 到 8，视文档密度调整 |
| 无引用处理 | 生产环境建议指定“不知道/未检索到依据”的回复 |

一个可用的系统提示词模板：

```text
你是公司内部知识库助手。请只基于已检索到的知识库内容回答。
如果知识库没有提供依据，请明确说明“当前知识库中没有找到可靠依据”，不要编造。
回答时优先给出结论，再给出步骤或依据。
涉及制度、金额、权限、审批、操作风险的问题，请提醒用户以最新正式文件为准。
```

这个提示词的关键不是“让模型更聪明”，而是限制它在没有依据时乱答。

### 2. 检索参数怎么调

RAG 调优优先级建议如下。

| 优先级 | 调整项 | 原因 |
| --- | --- | --- |
| 1 | 文档质量和切分 | 源数据错了，模型无法补救 |
| 2 | 向量模型 | 嵌入质量直接影响召回 |
| 3 | 检索模式 | 混合检索通常对业务文档更稳 |
| 4 | TopK | 太小容易漏召回，太大会带入噪声 |
| 5 | 相似度阈值 | 阈值太高无答案，太低容易答错 |
| 6 | 提示词 | 用于控制输出边界，不应用来掩盖检索问题 |

常见故障和处理方式：

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 答案很流畅但不对 | 没有命中正确分段，模型自由发挥 | 提高无引用约束，调整分段和检索 |
| 经常回答“不知道” | 相似度阈值过高或问题表达和文档不一致 | 降低阈值，开启问题优化，补充关联问题 |
| 引用内容太杂 | TopK 太大或文档切分过粗 | 降低 TopK，重新切分 |
| 同义问法命中差 | 向量模型弱或文档术语单一 | 换向量模型，补充 FAQ 问法 |
| 多轮对话跑偏 | 历史记录带入无关上下文 | 降低历史轮数，明确当前问题优先 |

## 七、高级智能体：什么时候需要工作流

简易智能体适合“问答型应用”。当你需要执行多步骤业务流程时，就应该考虑高级智能体。

适合使用高级智能体的情况：

| 需求 | 示例 |
| --- | --- |
| 条件判断 | 用户是售前、交付还是运维，走不同回答流程 |
| 工具调用 | 查询订单状态、调用工单 API、读取数据库 |
| 多模型协作 | 一个模型做分类，一个模型生成最终答复 |
| 人工确认 | 高风险操作前让用户确认 |
| 多模态输入 | 处理图片、音频、视频相关节点 |
| 长流程任务 | 收集表单字段、生成报告、写入业务系统 |

工作流设计时建议遵守一个原则：每个节点只承担一个明确职责。不要把分类、检索、判断、生成、格式化都塞进同一个模型节点。这样初期看起来快，后期调试会非常困难。

## 八、发布和集成

智能体调试通过后，可以发布为问答页面，也可以嵌入第三方系统。官方快速入门文档提到，MaxKB 支持将智能体以全屏模式或浮窗模式嵌入第三方 Web 系统，也支持通过 API Key 进行对话接入。

常见集成方式：

| 方式 | 适合场景 | 注意点 |
| --- | --- | --- |
| 公开问答链接 | 内部试用、快速分享 | 控制访问权限，避免敏感知识外泄 |
| iframe / 浮窗嵌入 | 企业门户、文档站、业务系统 | 注意跨域、登录态、移动端适配 |
| API Key 调用 | 自研系统、客服系统、工单系统 | API Key 要分环境管理，做好调用审计 |
| 企业 IM 接入 | 飞书、钉钉、企业微信等 | 通常涉及 X-Pack 或额外配置 |

上线前至少完成这些验证：

| 检查项 | 标准 |
| --- | --- |
| 权限 | 非授权用户不能访问敏感智能体和知识库 |
| 引用 | 关键回答可以追溯到知识库片段 |
| 边界 | 问到知识库外内容时不编造 |
| 延迟 | 常见问题响应时间可接受 |
| 成本 | 云模型 token 成本可估算 |
| 日志 | 能定位失败请求、用户问题和模型输出 |

## 九、生产环境建议

如果 MaxKB 用于真实业务，至少补齐下面几类工程能力。

### 1. 数据备份

需要备份的对象包括：

| 对象 | 原因 |
| --- | --- |
| PostgreSQL 数据 | 用户、配置、知识库元数据、对话记录等 |
| 向量索引和文件数据 | 知识库实际内容和检索能力 |
| 环境配置 | 端口、域名、模型供应商、密钥配置 |
| 自定义工具代码 | 工作流和工具调用依赖 |

备份不是“有一份压缩包”就够了，还要定期做恢复演练。不能恢复的备份等于没有备份。

### 2. 安全配置

上线时建议至少处理：

| 项目 | 建议 |
| --- | --- |
| 默认密码 | 首次登录后立即修改 |
| 公网暴露 | 能内网访问就不要公网暴露；必须公网则放在 HTTPS 和反向代理后 |
| API Key | 不要写进文档，不要放前端，不同环境分开 |
| 权限 | 按知识库、智能体、工具分别授权 |
| 审计 | 保留对话日志和工具调用记录 |
| 升级 | 关注安全修复版本，尤其是认证、SSRF、Webhook、API Key 相关问题 |

MaxKB 在 2026 年的版本更新中已经多次涉及安全修复，例如认证、回调 URL、Webhook 触发等方向。生产环境不建议长期停留在旧版本。

### 3. 评估体系

上线 RAG 应用时，建议维护一份固定测试集。

| 指标 | 说明 |
| --- | --- |
| 检索命中率 | 正确分段是否出现在 TopK 结果里 |
| 答案正确率 | 最终回答是否符合业务事实 |
| 引用一致性 | 回答内容是否能被引用片段支持 |
| 拒答准确率 | 知识库没有依据时是否拒答 |
| 响应延迟 | P50、P95、P99 延迟 |
| 单次成本 | 每类问题消耗的 token 或本地 GPU 资源 |

对于企业应用，评估集要包含真实用户问法，而不是只放文档标题式问题。真实用户不会说“请说明报销制度第三章第二节”，他们更可能问“我周末打车能不能报”。

## 十、一个推荐的最小落地方案

如果你是个人开发者或小团队，可以按下面这个配置起步。

| 层级 | 推荐方案 |
| --- | --- |
| 部署 | 单台 Linux 服务器 + Docker / 官方离线安装 |
| 模型 | 云模型先跑通；后续接 Ollama 或 vLLM |
| 向量模型 | 先用供应商向量模型，稳定后再换本地 |
| 知识库 | 先整理 20 到 100 篇高质量文档 |
| 智能体 | 先做简易智能体，再逐步拆高级工作流 |
| 评估 | 准备 50 个真实问题做回归测试 |
| 运维 | 定期备份 + 版本记录 + 访问控制 |

推荐实施顺序：

1. 用 Docker 在测试机跑起来。
2. 接入一个云端 LLM，确认普通问答正常。
3. 接入向量模型，创建一个小知识库。
4. 用 20 个真实问题做命中测试。
5. 创建简易智能体并限制“无依据不回答”。
6. 发布内部试用链接。
7. 根据日志调分段、TopK、阈值和提示词。
8. 稳定后再考虑高级工作流、工具调用和业务系统集成。

## 十一、常见问题

### 1. MaxKB 和 Dify 怎么选？

Dify 更像通用 LLM 应用平台，工作流、应用发布、模型接入和插件生态更泛化。MaxKB 更强调知识库问答、企业智能体和快速嵌入业务系统。如果核心需求是企业文档问答和客服知识库，MaxKB 上手更直接；如果你需要更复杂的多应用编排和团队低代码平台，可以同时评估 Dify。

### 2. MaxKB 和 Open WebUI 怎么选？

Open WebUI 更适合做私有 ChatGPT 入口和本地模型聊天界面。MaxKB 更适合把文档知识、智能体、工具和业务集成组合起来。两者不是完全替代关系。

### 3. 知识库问答不准，是不是模型不够强？

不一定。RAG 问答不准通常先看检索：文档是否干净、切分是否合理、向量模型是否合适、TopK 是否过小或过大、相似度阈值是否过严。只有检索结果正确但生成答案仍错，才优先怀疑大语言模型或提示词。

### 4. 能不能直接把大量 PDF 全部上传？

可以，但不建议一开始这么做。先选一批高频、高质量、结构清晰的文档跑通闭环，再逐步扩充。大量低质量 PDF 会让检索结果变差，后期清理成本更高。

### 5. 商用要注意什么？

MaxKB 开源仓库使用 GPL-3.0 许可证。内部自用、私有化部署和二次开发时，需要结合你的分发方式、修改方式和商业模式评估合规要求。模型权重、云模型 API、文档数据也各自有授权和合规问题，不能只看 MaxKB 本身。

## 十二、总结

MaxKB 的最佳使用方式，是把它当成一个“知识库智能体工程平台”，而不是单纯聊天界面。真正决定效果的不是页面上创建了多少智能体，而是三件事：

1. 知识库文档是否高质量、可检索、可维护。
2. 智能体是否明确边界，能在无依据时拒答。
3. 是否有评估、日志、备份、权限和版本管理。

对个人开发者来说，MaxKB 可以快速搭出一个可用的 RAG 应用；对企业团队来说，它的价值在于把模型能力接到已有知识和业务流程里。建议从一个小而真实的场景开始，例如“内部运维手册助手”或“产品 FAQ 助手”，先把命中率、引用一致性和拒答能力打磨稳定，再扩展到更复杂的工作流和工具调用。
