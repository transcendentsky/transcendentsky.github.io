# 写一篇值得读、值得赞同、值得收藏的 AI 文章

目标是让特定读者解决一个具体问题，并获得可信、可复用的新认识。通过明确的阅读收益、逐层解释和实用交付物改善传播机会；阅读量、赞同和收藏还受账号、曝光、时机等因素影响，不承诺爆款。

## 1. 先确定核心主题、问题与文章承诺

从用户提供的主题、素材、草稿和发布场景中，确定：

- **读者起点**：普通用户、懂编程的入门者，还是已有经验的工程师；他们已经知道什么？
- **核心问题**：用一句读者会搜索或提问的话表述，范围应能在一篇文章内讲清。
- **阅读收益**：读完能解释一个现象、复现一个流程，或做出一个选择。
- **独特增量**：相较已有介绍，多了哪个例子、解释、实验、失败分析或判断框架？

先区分主题名和核心问题：“RRSI”是对象，“为什么递归自我改进需要正则化，具体怎样起作用”才是组织全文的问题。动笔前用一句话写出中心论点，再选出支撑它的关键概念、机制与证据；标题、案例、公式和图片都应服务于这条主线。用户已给定核心角度时，以该角度组织材料。

信息缺失时采用合理默认并简短说明；只有缺失信息会改变文章方向时才提问。默认面向有基础计算机常识的中文读者，输出适合知乎或个人博客的 Markdown。篇幅由解释所需证据决定。

用户尚未确定选题时，提供少量候选，并比较读者需求、已有内容缺口、可获得证据和作者经验。优先选择有材料支撑的具体问题，例如“为什么知识库里有答案，RAG 还是答错”，而不是“大模型全面解析”。

**完成条件**：能写出“给谁看—回答什么核心问题—中心论点是什么—凭什么相信—带走什么”的简短定位；正文范围能围绕它收束。

## 2. 建立证据与写作角度

当需要了解知乎写法、解释技能依据或重新调研热门文章时，读取 [知乎 AI 文章调研](references/zhihu-ai-writing-research.md)。其中的风格观察用于启发结构，不能替代技术证据。

写作前建立简短的内部证据清单：核心主张、来源、适用版本或日期、已知限制。涉及模型能力、价格、榜单、工具接口等易变信息时查询当前资料；技术结论优先核对原论文、官方文档、代码或可复现实验。不能联网时明确核实范围，收缩结论。

区分论文报告、作者实测、演示例子和个人推断。论文中的成绩保留模型版本、数据集、指标和评测条件；成本区分训练、研发与推理，性能区分延迟、吞吐与质量。不同设置下的结果不能直接排名。

第一人称经验只使用用户提供或实际完成的经历。未运行的代码标为示例或未验证，不写成已复现；资料不足时给出验证方法或明确保留问题。不得编造测评、引用、互动量或读者反馈。

**完成条件**：支撑标题和主结论的证据已落实，未知内容已删去、限定或标明。

## 3. 选择适合问题的结构

先在内部写一条能串起全文的逻辑链，说明读者为什么需要下一节。按核心问题安排材料，而不是按收集顺序或术语清单堆章节。背景建立问题，分类拆解问题，机制回答问题，流程连接机制，实验检验答案，总结回扣核心问题；取舍由主题决定，避免把这个顺序机械套用于所有文章。

例如，围绕“正则化”解读 RRSI 时，适合采用“自我改进为何过拟合 → 三类过拟合 → 各类风险对应的正则化 → 整体演化流程 → 实验与总结”。此时“提案端／选择端”可用于流程讲解，但不应取代已经确定的正文主线。

下面是可选骨架，按材料调整，不把每篇文章写成同一种模板。

| 类型 | 推荐推进方式 | 读者带走的东西 |
| --- | --- | --- |
| AI 科普 | 一个熟悉的现象或困惑 → 一句话回答 → 贯穿案例 → 拆解机制 → 类比失效处 | 能复述的解释、误区对照 |
| 技术原理 | 现有方案遇到的问题 → 整体数据流 → 关键模块 → 必要公式或代码 → 代价与边界 | 心智模型、关键推导或结构图 |
| 工程实战 | 目标与适用条件 → 最小可运行路径 → 输出验证 → 故障定位 → 方案取舍 | 可执行步骤、检查表、排错路径 |
| 技术观点或选型 | 明确判断与前提 → 对比标准 → 证据和反例 → 分场景建议 | 有条件的决策规则 |

先给输入、输出和整体关系，再进入零件。选一个小而完整的案例贯穿全文：每引入一个机制，就说明它怎样改变这个案例的结果。

每节回答一个真实问题。用“为什么查到了文档还是答错”这类标题指明阅读目的；概念标题在检索和定位更方便时也可以保留。进阶推导、历史沿革和扩展资料放到附录，保护主线。

**完成条件**：每节都有明确的阅读问题，能说明它承接了什么、为下一节解决了什么；各节合起来形成论证链，主线没有依赖尚未解释的概念。用户指定的论述顺序优先落实到正文，再安排实现细节。

## 4. 写标题与开头

正文论点稳定后，给出约 3 个不同角度的标题，并推荐一个。优先呈现具体对象、读者困惑或可验证收益，自然保留读者会搜索的关键词。

示例标题仅展示构造方式，不代表调研样本或已证实结论：

- 问题型：`为什么你的 RAG 查到了资料，还是答错？`
- 解释型：`从一句话的生成过程，理解 KV Cache 在缓存什么`
- 实战型：`给知识库问答做评测：从失败样例到排错表`
- 取舍型：`长上下文还是 RAG？先看这几种失败场景`

标题中的数字、速度提升、时间承诺和“零基础”等词，都要由正文兑现。用清楚的对象与收益吸引读者，避免凭空制造震惊、身份优越感或失业焦虑。

开头尽快完成三件事：让读者认出自己的困惑，给出简短回答，说明本文会怎样证明或演示。根据主题决定是否需要背景，避免从 AI 发展史写起。

原创开头示例：

> 知识库明明有退款规则，机器人却说“查不到”。问题可能发生在检索阶段，也可能发生在证据拼接或答案生成阶段。本文用同一条退款问题走完这条链路，最后给出一张能直接用于排错的检查表。

## 5. 把复杂技术解释清楚

- **先展示，再命名**：先用案例呈现问题或操作，再引入术语，并说明它解决哪一步的困难。
- **逐层增加精度**：直觉解释 → 具体过程 → 必要的正式定义。公式解释符号、输入输出与作用；科普可减少公式，保留因果机制。
- **给类比划边界**：明确类比对应技术中的哪些对象，以及在哪一步不再成立。模型拟人化表达随后还原为具体计算或训练过程。
- **把替代方案带进来**：解释为何需要新机制时，展示更简单方案会在哪里失败；比较时保留任务和资源前提。
- **让证据紧邻结论**：图表、代码或案例之后解释“它说明什么、还不能说明什么”。一个回答样例只能作演示，不能证明整体能力。

正文用自然的中文解释，专业词首次出现时给简短释义。段落围绕一个意思展开，列表用于步骤或并列条件，加粗用于少量关键判断。删掉重复的背景、空泛形容词和没有展开的“显而易见”。

实战文章保留必要的环境、依赖版本、输入数据、运行命令、预期输出和常见失败信号。缩短到读者能完成的最小闭环，再解释扩展；有实际测试时记录测试范围。

### 配图要参与论证，优先检查原文图

为主要解释难点和关键证据选择配图：机制关系用架构或流程图，实验结论用结果图，取舍可用比较表。每张图都要回答正文中的具体问题，不按固定数量凑图。

解读论文或融合原文时，先查看原文的关键图及图注，优先选用与主线相关、版本一致且可读的原图。原图已清楚表达机制或结果时直接使用；需要中文简化、局部拆解或新增比较时再补充原创示意图，避免用装饰图或重复重绘替代原始证据。

取得并实际查看图片后再引用：可下载作者公开提供的图，或从原 PDF 提取、渲染相关图区。保持轴、单位、图例、误差线与必要子图完整；裁切、翻译标注或重绘时在图注说明，不能改变原意。读图时核对比较对象、统计口径与版本；正文数据与原图不一致时，先查明差异。

把图放在相关解释或证据旁，提供可理解的替代文本。图注写清作者／论文、原图编号、版本和来源链接；正文用几句话解释应关注哪部分、支持什么判断，以及不能推出什么。引用原图与原创图明确区分，遵循原图适用的使用条件，不将他人图片标为自己的作品或自行变更其许可。

按项目惯例保存图片并检查页面显示与缩放后的可读性。无法获取或读清原图时，说明实际限制，再选择准确重绘或配图建议；不要把尚未取得的图片写成已插入的原图。

## 6. 设计收藏与讨论价值

根据主题提供一个有用的交付物：排错表、决策树、最小示例、核对清单、术语关系图或带学习顺序的资料路线。它应能在读者下次遇到问题时直接使用，并注明适用条件。

结尾回到开头的问题：给出当前能支持的答案、最容易误用的边界，以及下一步行动。需要讨论时提出有条件的具体问题，例如“如果召回已通过，下一步你会如何区分上下文截断和生成失败？”互动邀请保持简短、可选。

将以下关系视为编辑假设，发布后再验证：

- 阅读机会：读者需求明确，标题准确表达收益，开头迅速交付信息。
- 赞同机会：解释带来新认识，判断有证据，承认限制。
- 收藏机会：有清晰、可检索、可再次使用的材料。

## 7. 交付前审稿

逐项检查并修复问题，不用一个总分掩盖事实错误：

- 标题的主要承诺是否在正文兑现？
- 是否只有一条清晰的核心主线，各节按合适的逻辑推进，而非罗列知识点？
- 主结论能否追溯到来源或明确标注的推断？时效与版本是否匹配？
- 目标读者是否能沿着案例理解每一步，类比是否保留了关键限制？
- 技术文章是否解释机制与取舍，实战文章是否形成运行与验证闭环？
- 是否存在真实的信息增量和可复用交付物？删掉某段后无损理解的，优先删减。
- 引用与改编是否注明来源？是否残留未完成的图、虚构的经验或无依据的数字？
- 配图是否解释关键机制或支撑证据？原图的编号、版本、图注与正文是否一致，局部文字和图例是否可读？

默认交付：推荐标题及少量备选、文章正文、参考资料，以及确实影响发布的待核实项。把编辑说明和待办放在正文之外。用户只要正文或仅要求改稿时遵循其格式，不附加完整过程报告；未经要求不代为发布。

## 8. 用真实反馈迭代

用户提供后台数据后，在同一统计窗口和口径下观察曝光、阅读、赞同、收藏、评论与关注转化。只有分母可用时才计算对应比例；公开赞同和收藏总数无法推出阅读转化率。

结合评论定位问题：读者是否被标题吸引却未得到答案，是否在同一个概念处卡住，是否需要更方便复用的材料。每轮优先调整一个主要变量，并记录修改时间。前后数据变化只能提供线索；没有可比曝光与对照时，不把增长归因于某种写法。
